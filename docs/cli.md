# CLI commands

The skill calls these; you rarely need to. `codechart <command> --help` lists every option.

| Command | Purpose |
|---|---|
| `codechart check` | Which rules apply to changed files. `--files <csv>`, `--git`, `--commit <sha>`, `--since <base>` (+ `--head <ref>`), `--matched <csv>`. On a release branch (`release.branches`, unless `release.auto` is `off`) the JSON also has `release`: `{ action: suggest\|draw\|done, branch, version?, path? }`, see [Release map](release-map.md#on-release-branches) |
| `codechart render <spec>` | Render a spec (JSON file or `-` for stdin). `--output auto\|cli\|web\|both`, `--theme auto\|light\|dark`, `--open`, `--md` (paste-ready markdown), `--at <rev>`; `--git`, `--commit <sha>`, `--since <base>` (+ `--head <ref>`) to check claims against the diff (refused for an [explain map](explain-map.md), which has none); `--tech <spec.json>` for a [business map](business-map.md) (the tech map its items link to; default: the newest saved map on the branch); `--strict` to exit 1 on a mismatch or on drift from the saved plan without a reason (a plan rendered in a git repo is kept per branch for a week, and the summary after it prints a `Plan vs built` block, not with `--at`/`--head`, and only when its `--git`/`--commit`/`--since` range starts at or before the plan's commit: see [design](design.md)); `--pr` prints a map's PR/MR description section and writes its SVG to the cache folder (`--svg <file>` writes it elsewhere, `--image-url <url>` sets where the description loads it) |
| `codechart setup-pr-maps` | Add the CI job for [PR maps](pr-maps.md): shows the change and asks first. `--yes` (no question), `--pr` (open a pull/merge request instead of writing to the work tree), `--host github\|gitlab` |
| `codechart pr-sync` | In CI: redraw the map section of this PR or MR's description against its latest commit (see [PR maps](pr-maps.md)) |
| `codechart release-context` | JSON of what was merged since the last release, for an agent: first-parent commits oldest first, each with title, date, PR/MR number, changed files (first 40) and, when `gh` or `glab` works, the PR's text and tech map. `--since <ref>` (default: newest `v*` tag before HEAD; with none, a first release: every commit from the start), `--head <ref>`. Without `gh`/`glab` it uses git only and says so in `notes`; a number that isn't a PR skips just that change's text, listed in `notes` |
| `codechart schema` | Spec JSON schema; `--flow` for flow specs, `--business` for [business maps](business-map.md) (`--business --explain` for a page that explains an area), `--release` for [release maps](release-map.md), `--config` for the config file |
| `codechart config` | Config in effect and where each value comes from (`--json`) |
| `codechart init` | Write a commented starter `.codechart.yaml` at the git root (`--force` to overwrite) |
| `codechart install-skill` | Install the skill for the agents found in your home folder. `--agent <names>`, `--dir <path>`, `--force` to overwrite a folder that isn't an older codechart copy, `--no-reminder`, `--no-hook`, `--no-plugin` (or `--reminder`, `--hook`, `--plugin` for only one). See [Install and agents](install.md) |
| `codechart update` | Install the newest codechart with npm and refresh the skill copies, reminder lines and OpenCode plugin copy you have; `--check` only reports. See [Updating](install.md#updating) |
| `codechart uninstall` | Remove the skill, reminder lines, hooks and OpenCode plugin file; `--skill`, `--reminder`, `--hook`, `--plugin` to pick some |
| `codechart doctor` | Check that your agents can find codechart: per detected agent the skill (current, outdated, missing, or a folder that isn't codechart's), the reminder line, the Claude Code hook and the OpenCode plugin file, plus `codechart` on PATH and its version against the newest npm one seen (no network). Problems end with the command that fixes them: ✗ for a skill or CLI that is missing, outdated or not codechart's (exit 1), ⚠ for a missing reminder, hook or plugin, which you may have opted out of (exit 0); an outdated plugin copy, or a file of that name that isn't ours, is a ✗ (`--fix` refreshes only the outdated one). Agents sharing a skill folder show it once. `--fix` runs the ✗ fixes itself (never over a skill folder that isn't codechart's), only names the opt-in ones, and checks again. `--last` explains why the last turn in this repo did or didn't get a diagram (Claude Code, OpenCode). See [No diagram appeared](install.md#no-diagram-appeared) |
| `codechart hook prompt\|stop` | Run by the Claude Code hook (OpenCode's plugin runs inside OpenCode, not through this command); reads the hook's JSON on stdin and logs its decision for `doctor --last` |
| `codechart review` | Write review notes on the newest map of this branch in `$VISUAL`, `$EDITOR`, or `vi` (`notepad` on Windows): see [Console review](#console-review). `--change <title>` picks another map (its title or file name slug; any case), `--print` prints the document instead of opening an editor |
| `codechart comment <node>[:<path>:<line>] <text...>` | Add one pending note. `--kind comment\|question\|delete` (default comment), `--side old\|new`, `--change <title>` |
| `codechart feedback` | Print the pending notes as numbered markdown for an agent. `--take` marks them sent, `--copy` also copies them (OSC 52, on a terminal), `--change <title>`. `--import` first saves the notes copied from a page with *Finish review*: see [Notes from the page](#notes-from-the-page) |

## Console review

Every map or flow `render` draws gets a `<same name>.review.json` in the cache folder, whatever the output mode (`cli`, `--md` or a page); a page, when there is one, sits beside it. It holds the map's title and file name slug (a flow's slug ends in `.flow`), its branch, each node's id, label, path and the diff lines the map showed, and your notes. The map a command works on is the newest one on the current branch, or the one named by `--change`. None on this branch: `No map to review on branch <branch> yet. Ask your agent for a map first.`

`review` opens a text file:

```
# Review: Orders and coupons · branch feat/coupons · drawn at 09:05
# Add a note on its own line under a node or a diff line:
#   > text    comment        >? text   question       >del text  delete this
# To go on to a new line in a note, start the next line with "  > " (two spaces first).
# Lines starting with # are ignored. Save and quit when you are done; quit without saving to cancel.

## Order — app/orders.py  [Order]
@@ -1,2 +1,2 @@
   1  class Order:
-  2      pass
+  2      coupon = Column(Text)
>? is this nullable?

# Unchanged on the map (you can still note on them):
## Queue  [Queue]
```

The file is named after the map (`<title-slug>.diff`) so editors colour it as a diff; for `vi`, `vim`, `nvim`, `gvim` and `mvim`, codechart also turns syntax on (macOS's system vimrc leaves it off) and highlights `>` notes and `##` headings. `review --print` on a terminal colours the same way (red `-`, green `+`, cyan `@@`, dim `#`, bold headings, notes black on yellow); piped, or with `NO_COLOR` set, it is plain text.

A node heading is `## label — path  [id]`; the id in brackets is what the file is read by (and what an agent uses). Nodes with a diff come first, in map order; nodes without one are listed at the end. A node on the same file and diff as an earlier one says `# Same diff as "<label>" above.` instead of repeating it; notes under it are about the node. Diff rows are a sign, the line number and the code (new line numbers; old ones on `-` rows). Lines starting with `#` are ignored. A note is a line starting `>` (comment), `>?` (question) or `>del` (delete this); its further lines sit right under it, each starting with spaces and `>` (`  > more`), so a note of several lines comes back whole and none of its lines is read as a diff row; a note under a diff row points at that line (`+` and context rows: new side; `-` rows: old side), one under a node or hunk heading at the node. An empty note is dropped; a note above the first node, or under a heading you changed, can't be placed: `review` says which line, saves nothing, exits 1 and keeps the file, printing its path, so nothing you typed is lost. Line endings (LF, CRLF) don't matter. Saving replaces all pending notes with the ones in the file (the ones already there come back as `>` lines to edit or delete); notes already sent to your agent, and outdated ones, show as `#` comments and are untouched. Quitting without saving, or an editor exit status other than 0, saves nothing. If the code changed since the map was drawn (HEAD or the uncommitted files, for a map drawn with `--git` or `--since`), `review` warns first and shows the map's snapshot anyway.

`feedback` prints `# Review feedback: <title> (N notes)` and each pending note as `N. label (path:line, new line)  [id]` (`old line` for a removed one; node-level notes show the path only), the quoted line, then `Comment:`, `Question:` or `Delete:` and the text. `--take` then marks them sent, so the next run says `No pending review notes.` A note on something other than a node or line reads `N. On the arrow Order → Coupon`, `On the gap “…”`, `On the not-on-map item “…”`, `On the plan-vs-built note of <label> (not built)` or `On the title`.

### Notes from the page

A page with a review file takes notes too (see [Review on the page](review.md#on-the-page)). *Finish review (N)* copies them as plain lines and a closing line `codechart review · N notes · <token>`; the token holds each note's place and kind and which map they belong to; the words are read from the numbered lines, so copy the whole text. A business page sends a shorter token (about 200 characters for 5 notes) and shows that closing line cut to one line in its dialog; the copied text still has all of it.

`codechart feedback --import` reads that text from stdin when it is piped in, else from the clipboard (`pbpaste` on macOS, `Get-Clipboard` on Windows, `wl-paste`, `xclip` or `xsel` elsewhere), finds the map by its file name slug and branch, and adds the notes to its review file: `✔ Imported 3 notes into "Orders and coupons"`. Without `--take` it then prints the pending count (`3 notes saved — 2 comments · 1 question · 0 deletes`); with `--take` it prints and marks them sent, as `feedback --take` does (the agent skill pipes your pasted text into `feedback --import --take`). A note already saved is skipped (`Nothing new to import`), so pasting twice is harmless. A note on something the map no longer shows, or on a node whose diff changed since the page was drawn, comes in `outdated`. No closing line: `No codechart review found.`; a broken token: `The codechart review is damaged`; numbered lines that don't fit the token: `The review text doesn't match its last line`; over 512 KB: refused. A business page's record is kept 30 days; after that: `No business page called "<slug>" on branch <branch>: its saved record is gone`. `--change` can't be combined with `--import`.

### Explain maps

`codechart render` takes a map spec with `"kind": "explain"` (shape: `codechart schema`): boxes with the status `existing` (in the area; `path` required) or `outside` (a neighbour the area talks to; `path` optional, none for an external service), and no change marks, `drift` or `omitted`, and up to five `flows` (shape in `codechart schema`): step-by-step behaviours of the area, each with the same steps, labelled branches and anchors as a flow spec, every step `existing` and optionally in a box (`box`: a box id). It draws like any map (terminal block, page and review file) but shows the code as it is: `--git`, `--commit`, `--since` and `--head` are refused (`--git, --commit, --since and --head do not apply to an explain map…`), and so is `--pr` (`explain maps are not for PR descriptions`). `--at <rev>` still reads the files at another revision. Nothing is saved as a plan, there is no plan vs built, and no `diff not checked` or `not on map` line. The count line reads `4 boxes · 2 outside · ✓ 3 checked · 1 not checkable`. With flows the page gets a **Components** and a **Flows (n)** tab (the Flows tab and its diagrams are in the page only; `--output cli` writes no page), the header counts boxes and steps (`✓ 9 boxes and 12 steps checked against the code`), and stdout ends with `Flows on the page: Refund an order · Create invoices for paid orders`. A step or branch whose anchor doesn't resolve is a `✗` mismatch like a box, not a failed render (`--strict` exits 1); `--at` reads boxes and steps from another revision. See [Explain map](explain-map.md).

### Business maps

`codechart render` takes a business spec (`"diagram": "business"`, shape: `codechart schema --business`) and writes one HTML page, printing one summary line and its link (`--md`: the same as a paste-ready block). It is HTML only: `--output`, the diff flags and `--at` have no effect, and `--pr` is refused (`business maps are not for PR descriptions`). `--tech <spec.json>` names the technical map's spec; without it the newest saved map or flow on the branch is used, and with none the render stops: `no tech map found for this change: render the tech map first, or pass --tech '<spec.json>'`. `--tech` on any other spec is an error. The render also stops, listing each one, when a link is not a box on that map, an item has no link, or a sentence looks like code, a file name or path, a web address, a setting name, a secret or a technical map id. See [Business map](business-map.md).

With `"kind": "explain"` the spec explains how an area works today (`codechart schema --business --explain`): one `flow` (`lanes` of who acts, `steps` with a `lane`, `links` and `evidence`, and `arrows` between them; a step ending in "?" is a question with a labelled arrow per answer), rules with `rule` and `exceptions`, `cases` (`situation`, `outcome`) and saved data, each with `links` and `evidence`. `journeys` and `questions` are refused. Links are boxes of an explain map or flow steps (`flow:<flow>/<step>`); the map is `--tech '<explain spec.json>'`, else the saved explain map named by the spec's `map` slug, else the newest one. Saved maps are looked up on the current git branch only: one drawn on another branch is not found, even by name (`no explain map found for this area…`), so pass `--tech`. A change map is refused for it, and an explain map for a change spec. The page is read-only (no notes, Yes/No, answers or send bar) and saves no review file, so there is nothing for `feedback --import` to read. `--explain` only applies to `--business`.

### Release maps

`codechart render` also takes a release spec (`"diagram": "release"`, shape: `codechart schema --release`): a title, `version`, `date`, `summary`, optional `since`, and 1 to 12 `sections`, each with a `change` (`new`, `changed`, `fixed`), a summary, an optional `pr` number and business-map items without `links`, `evidence` or questions (up to 4 journeys, 6 rules and 4 saved data items); a spec with `questions` or `evidence` is refused. It writes one static HTML page (no script, no review file) and prints that page to a PDF next to it with an installed Chromium-based browser in headless mode. It prints the summary line, `PDF: <path>` and the page link (`--md`: a paste-ready block). `--pdf <file>` chooses the PDF path (absolute or relative, ending in `.pdf`, in an existing folder); it is an error for other specs. With no browser, or if it fails, the page is kept, one line on stderr says so, and the exit status is 0. `--pr` and `--tech` are refused. The page is saved as `<stamp>-v<version>--<title>.release.html`. The product name, logo and browser come from `release.product`, `release.logo` and `release.browser` in [configuration](configuration.md). See [Release map](release-map.md).

Notes sent back from the page (*Send back to developer*) go through `feedback --import` as above, with three more kinds: `Answer:` (to a question), `Confirmed:` and `Rejected:` (the owner's yes or no on the agent's reading), next to `Comment:`. Each note is headed by its item, e.g. `Rule "Manager approval" [R2] (links: approvals)`; an answer also says what it is about. The count line reads `3 notes saved — 1 answer · 1 confirmed · 1 rejected · 0 comments`. Plain `codechart feedback` shows the newest business page's notes when it has unread ones and the map has none (or is older), else the newest map's; `--change <title>` can name either.
