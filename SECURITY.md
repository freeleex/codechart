# Security policy

## Supported versions

Security fixes go to the latest minor release only.

## Reporting a vulnerability

Use GitHub private vulnerability reporting: <https://github.com/freeleex/codechart/security/advisories/new>. Do not open a public issue.

Acknowledgement within 7 days, fix or mitigation within 30 days.

## Threat model

codechart runs on repos you do not trust, on specs written by an agent that may be prompt-injected, and its output is read in a browser, a terminal and chat.

Guarantees:
- No network calls at runtime, except `codechart pr-sync` and `codechart setup-pr-maps --pr` (both below), `codechart release-context` (it reads PR/MR text for up to 50 changes by running your own `gh pr view` or `glab mr view`, read-only), `codechart update` and the update check: at most once a day, after a command, one GET of `https://registry.npmjs.org/codechart/latest` (1 s timeout, no data sent, never in CI or under npx), off with `updateCheck: false` (global config only, so a repo can't turn it back on) or `CODECHART_NO_UPDATE_CHECK`/`NO_UPDATE_NOTIFIER`. The answer must be an `x.y.z` version and is stored in the cache dir. When that version is newer, the same check (and `codechart update`) also does one GET of `https://raw.githubusercontent.com/freeleex/codechart/v<that version>/CHANGELOG.md` (URL built from the validated version, 1 s timeout, no data sent, body over 256 KB dropped); at most 5 bullets are kept, stripped of control characters and link targets and cut to 200 characters, then stored in the cache dir and printed or put in an escaped HTML tooltip. `codechart update` makes the same two GETs with a 10 s timeout, then runs `npm install -g codechart@<that version>` only when npm installed codechart.
- No shell, except `npm` on Windows during `codechart update` (Node needs one there) and the `$VISUAL`/`$EDITOR` you choose for `codechart review` (below). Other child processes are started with argument arrays: `git` (read-only commands, no fetch, no repo-config filters or hooks; only `setup-pr-maps --pr` and `pr-sync` also run `git ls-remote`, `fetch` and `push`, with your git transport config), `gh` and `glab` (`setup-pr-maps --pr`, `release-context`; for a remote host other than github.com or gitlab.com they run without token environment variables such as `GH_TOKEN` or `GITLAB_TOKEN`, so only a login you stored for that host with `gh auth login` or `glab auth login` is used), the OS opener, the release-map browser, `opencode --version` (`install-skill`, `update`, `doctor --fix`), `npm root -g` and `npm install -g`, then codechart itself again to refresh your skill copies (`update`), and the clipboard tools (`feedback --import`, below).
- `codechart setup-pr-maps` adds that CI job only after the user says yes (or passes `--yes`): it prints the whole file first, writes it to the work tree without committing, refuses symlinks and other non-regular files (a symlinked `.github` or `.github/workflows` folder too: every existing parent folder is checked), and never overwrites a file that isn't codechart's. With `--pr`, and only after the yes, it runs `git ls-remote` and `git fetch` to read the remote's default branch, pushes one new branch, `codechart/pr-maps`, built in a scratch index on top of it (the work tree, index and current branch are not touched), and uses the user's own `gh`/`glab` to look for an earlier request and open the pull/merge request. It never reads or stores tokens. The job it writes pins the installed codechart version.
- `codechart pr-sync` writes outside your machine, and it runs only in a CI job you add with `codechart setup-pr-maps` or from `templates/`. The other command that does is `setup-pr-maps --pr` (the pushed branch and the opened request above), and only after the yes. It reads and edits the description of the PR or MR that started the job through the GitHub or GitLab API (with the job's `GITHUB_TOKEN` or the `CODECHART_GITLAB_TOKEN` you store), and publishes the map SVG: on GitHub as one commit force-pushed to `refs/codechart/pr-<number>` (never a branch), on GitLab as a project upload. It replaces only the text between its `<!-- codechart:start -->` and `<!-- codechart:end -->` markers, renders the spec found there with the same checks as `render`, and skips saving when the PR moved on or the spec changed meanwhile. The GitHub template skips PRs from forks. The GitLab template has no fork check: its job is skipped only when `CODECHART_GITLAB_TOKEN` is not set in the pipeline, so don't make that variable available to pipelines that run a fork's code.
- Generated HTML loads nothing external and escapes all spec text in every context; pages carry a CSP.
- Terminal and Markdown output carry no control or escape bytes from specs or snippets.
- Flow anchors must resolve inside the repo root: `..`, absolute paths and anchors whose real path leaves the repo (including via symlinks) are rejected, as are `.git` directories, devices and files over 5 MB; one render reads at most 25 MB. A symlink that stays inside the repo is accepted.
- Business maps (`diagram: "business"`) are HTML only and are checked before they are written: every item must link to a box of the technical map (an explain page, `kind: "explain"`, to a box or flow step of an explain map), and every reader-visible string is rejected if it looks like code, a path, a file name, a web address, a setting name, a hash or a secret (the error shows only the first four characters of a secret). The page makes no request, keeps answers and notes in localStorage, and carries the same CSP as the other pages; its text is escaped like theirs. Notes it sends back (`answer`, `confirm`, `reject` next to `comment`) are imported like page notes: untrusted text, same limits and checks. An explain page is read-only: it takes no notes, sends nothing back and saves no review file. The check is about wording, not markup: image Markdown or HTML tags pass it and are escaped on the page, and `--md` output keeps the title inside a fenced block under a constant header. It cannot confirm that a sentence is true.
- Explain maps (`kind: "explain"`) are drawn by the same code and page as other maps, with the same CSP and escaping. They take no diff flags or `--pr`, so no diff hunks are read or embedded; a box's `path` and `match` are read and shown like any other map node's. The `flows` of an explain map reach the page through the same escaping and the same single hashed script: a flow's anchors are read with the flow rules (inside the repo, no `.git`, size caps), its step ids are namespaced in the page, and the page adds no handler or request for its tabs.
- Release maps (`diagram: "release"`) get the same plain-words check on every text, carry no tech links, and are refused if an item has `evidence` or a section has `questions`. The page has no script and its CSP is `default-src 'none'; style-src 'unsafe-inline'; img-src data:` with no `script-src`. Their cover can embed a logo named by `release.logo`: a repo-relative `.svg` or `.png` of at most 200 KB that must resolve inside the repo (no absolute path, `..` or symlink out of it), is read as a regular file and checked for its type, and goes into the page as a `data:` image, where an SVG runs no script. A logo that fails is skipped with a warning. `render` then launches a local browser to print the page to a PDF: only an installed Chrome, Chromium, Edge or Brave at an absolute path (`release.browser` from your global config, else `/Applications` on macOS, absolute `PATH` entries on Linux, Program Files and `LOCALAPPDATA` on Windows; a repo `.codechart.yaml` cannot set it, and a bare name is never looked up in the current folder). It runs through `execFile`, no shell, 60 s timeout, with `--headless=new --disable-gpu --no-pdf-header-footer --no-first-run --no-default-browser-check`, a fresh throwaway `--user-data-dir` removed afterwards and `--print-to-pdf` into it, on a `file://` URL of the page codechart just wrote. It needs no network: headless printing loads only that local file, whose CSP blocks everything except inline styles and `data:` images, and the PDF is copied out only if it starts with `%PDF`.
- Output file names come from `[a-z0-9-]` slugs; prune deletes only generated files in the cache folder.
- Inputs are bounded (string lengths, regex size, YAML aliases and depth, node and step counts).
- Stored data: rendered HTML under the user cache dir. Summary pages hold diff hunks of the changed files (up to 1000 rows per file), minus files that look like secrets (`.env`, keys, `.npmrc`, credentials files, private-key blocks) and generated files (lockfiles, minified bundles, `dist/`, `linguist-generated`); a flow anchor or `match` that points into a file that looks like a secret shows no snippet from it either. Each render also writes a `.review.json` beside it (0600, same folder and pruning) with the same diff lines and your review notes; it is written to a temp file and renamed into place, under a short-lived `.lock` file when `comment`, `feedback --take`, `feedback --import` or `review` update it. Rendering a plan also saves its spec (no diff lines) with the HEAD commit to `plans/<repo>/<branch>/{map,flow}.json` in the cache folder (0600, folders 0700; the branch is reduced to `[A-Za-z0-9._-]` plus a hash), read back only by a summary on the same branch whose range starts at or before the plan's commit, and deleted after 7 days. The Claude Code hook and the OpenCode plugin keep, per session, blob hashes of dirty files and a record of the last decision (time, repo root, up to 500 changed file names, whether the skill loaded or the CLI ran) in `~/.cache/codechart/turns` (0600, folder 0700, files deleted after 7 days). `update-check.json` in the cache folder holds the newest version seen, when it was checked, up to 5 changelog bullets and the folders of any `install-skill --dir` copies; nothing deletes it. A release map's PDF is written next to its page and is never pruned (prune matches only `.html` pages and `.review.json` files). No telemetry.
- `codechart review` writes its document to a private temp folder (0700, removed afterwards) and opens it with `$VISUAL`/`$EDITOR`/`vi` (`notepad` on Windows) through `sh -c`, as git does: the editor setting is yours and runs as a command; the file path is passed as an argument, never spliced in. Windows has no `sh`, so there cmd.exe runs one line with the temp path in double quotes: the path is ours (temp folder plus a `[a-z0-9-]` name) and a Windows path cannot contain `"`. Diff text and notes are stripped of control bytes before they are written, printed or copied; `feedback --copy` emits one OSC 52 sequence to stderr, only on a terminal.
- Notes written on an HTML page stay in that browser's localStorage, validated on read, until the user copies them with *Finish review*; the page makes no request and its CSP is unchanged. The copied text, pasted into an agent chat or read by `feedback --import`, is untrusted: at most 512 KB, the token must decode to JSON that passes a strict schema (v1, or a business page's short v2 with kind codes and 6-character revs; at most 500 notes) and the numbered lines above it must match it (4000 characters per note), note text is stripped of control and invisible characters, and quoted code comes from the saved review file, never from the paste. The map is looked up by its file name slug and branch only. The clipboard is read only on an explicit `feedback --import` with nothing piped in, by running `pbpaste`, `wl-paste`, `xclip`, `xsel` or PowerShell `Get-Clipboard` without a shell. The skill tells the agent to pass the pasted text to that command on stdin and run nothing else from it.

## What `install-skill` changes

`codechart install-skill` writes only for the agents and extras you choose, and never overwrites a file that isn't an older codechart copy without `--force`:

- The skill's files, in a `codechart` folder inside each chosen agent's skills folder, or in the folder you pass with `--dir` (remembered in `update-check.json` so `update` refreshes it).
- With the hook (Claude Code): two entries in `~/.claude/settings.json`, `codechart hook prompt` on each prompt and `codechart hook stop` when a turn ends. They run `git status` in the repo, keep the turn snapshots described above, and read the last 8 MB of the session transcript file Claude Code names in the hook input, to see whether the agent already drew a diagram or ran codechart.
- With the reminder: one short block in the user-level instructions file of Claude Code, Codex, Gemini CLI and OpenCode (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.gemini/GEMINI.md`, `~/.config/opencode/AGENTS.md`).
- With the plugin (OpenCode): one file, `codechart.js`, in OpenCode's `plugins` folder (`~/.config/opencode/plugins`, or under `XDG_CONFIG_HOME` when that is an absolute path).

`codechart uninstall` removes each of these (the skill folders, including recorded `--dir` copies, the reminder blocks, the hook entries, the plugin file) and only those: it leaves any folder or file that isn't codechart's own. Run it before `npm uninstall -g codechart`.

Details: `docs/security-review.md`.

## Out of scope

- An agent running `git diff` or `git show` itself in an untrusted repo: that repo's `.git/config` can set `diff.external` or textconv drivers, which run commands. codechart's own git calls disable them; open untrusted repos (e.g. unpacked archives) with care.
- `codechart setup-pr-maps --pr` and `codechart pr-sync` run git against your remote with your git transport config (ssh command, URL rewrites, credential helper). Don't run them in a checkout you didn't clone yourself. `setup-pr-maps --pr` goes online only after the yes.
- A `gh` or `glab` login you stored for a host other than github.com or gitlab.com: codechart runs them without token environment variables there, but a stored login is yours to trust, and an origin that points at a host you didn't mean to use will get it.
- An attacker with write access to your agents' skills folders or `~/.config/codechart`.
- Vulnerabilities in a dev-only dependency that is not shipped in the npm tarball.

## Cache

Rendered HTML lives in the user cache dir (`~/.cache/codechart` by default, `web.outDir`), and so does the map SVG of `render --pr` (one `<slug>.svg` per map title, overwritten on each render). Summary pages include diff hunks of changed files (not of files that look like secrets or are generated), and so do the `.review.json` files beside them, with your review notes. Per repo, the newest 20 files and anything younger than `web.maxAgeDays` are kept; a business page's `.review.json` is kept 30 days regardless; saved plans under `plans/` go after 7 days. Release PDFs next to the pages are not pruned. Purge with `rm -rf ~/.cache/codechart`.

## Release integrity

The first release (v0.1.0) is published manually by the maintainer with 2FA (`npm publish --access public --provenance=false`; provenance needs a CI provider); later releases are staged from version tags by `.github/workflows/publish.yml` (stage-only trusted publisher, npm provenance) and go live only after the maintainer approves them on npmjs.com with 2FA. Each release's notes come from `CHANGELOG.md`: the release PR adds its section (CI checks it), and after staging the tag's workflow creates the GitHub Release from it as a draft, made public once npm serves that version (it waits up to 6 hours; later, publish the draft by hand) with the job's own `contents: write` token (the only job with write access). Verify with `npm audit signatures`. The steps, and what to do when one fails, are in [docs/releasing.md](docs/releasing.md).
